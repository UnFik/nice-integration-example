# sharedservice-oauth/backend (`nadi`)

[Bahasa Indonesia](README.md)

The backend of the [`sharedservice-oauth`](../README.en.md) example: a NICE SharedService in `nice_token` mode with the slug `nadi`, written in Go (`net/http`) with the reference library `nice-auth-sdk/verify`. Clients call this service directly with a NICE access token; NICE is not on the request path. The service verifies the token itself according to the [token verification contract](../../../nice/docs/token-verification.md), keeps data apart per organization and project, and checks sensitive operations online with NICE. The same backend also serves the UI in [`../web`](../web/README.en.md) as its backend-for-frontend (`/auth/*`, through `nice-auth-sdk/credentials`); how it works, the UI checklist and the browser tests are in [`../README.en.md`](../README.en.md).

Tested against nice revision: SDK `v0.1.0` and a local NICE server in Docker (the `nice:dev` image from `c7a3e33`), 2026-11-19, for the Bearer service: the image was rebuilt and `scripts/smoke.sh` passes. For the UI flow see [`../README.en.md`](../README.en.md). The `perms_ref` path ("Trying permissions that do not fit a token") was tested by hand on 2026-11-23 against `nice` `b9eb8b3` and SDK `4c9649d` (released as `v0.2.0`): a token of 154 permissions was issued with `perms_ref`, the UI read, created, and deleted a device, and NICE received one resolution per `nadi` process.

The layout follows a module of the `nice` backend (`nice/AGENTS.md`, "Struktur satu modul"), scaled down to one service with one resource (`device`). One action per file keeps code easy to find, the `deviceusecase` and `devicedto` packages are imported with explicit aliases, and dependencies only flow inward: adapters call use cases, and use cases and the domain never import `net/http`. The route table in `adapter/rest/device/device_routes.go` stays the single source of truth that the tests compare with the OpenAPI document.

## Operations

| Operation | Permission | Sensitive |
|---|---|---|
| `GET /devices` | `nadi.devices.read` | |
| `GET /devices/{id}` | `nadi.devices.read` | |
| `POST /devices` | `nadi.devices.create` | |
| `PUT /devices/{id}` | `nadi.devices.edit` | |
| `DELETE /devices/{id}` | `nadi.devices.delete` | yes, checked online with NICE |

`GET /healthz`, `GET /openapi.json`, and `GET /docs` (Swagger UI; its assets load from the jsdelivr CDN) are open without a token and are not in the OpenAPI document. On `/docs`, press **Authorize** and enter `Bearer <JWT>` to try an operation. After the import, the NICE catalog has the roles `nadi.viewer` (read), `nadi.admin` (every permission), and `nadi.editor` (read, create, edit; from `x-nice-roles`).

Device body: `{"name": "...", "serial_number": "...", "status": "active", "location": "..."}`. `name` is 1 to 120 and `serial_number` 1 to 64 characters after trimming surrounding spaces, `status` is one of `active`, `inactive`, `maintenance`, and `location` is optional (at most 120 characters, empty by default). Application errors use the same shape as `niceauth/verify`: `{"error": "...", "error_description": "..."}`, e.g. `400 {"error":"invalid_argument","error_description":"name"}` and `404 {"error":"not_found"}`.

Behavior worth knowing:

- The tenant is `nice_org_id` and the project is `prj` from the verified token, never a header, parameter, or body. An organization that calls for the first time gets a tenant at once (`ProvisionOnFirstUse`). A token without `prj` is answered `403 {"error":"insufficient_scope","error_description":"project_required"}`. Without `DATABASE_URL` data lives in memory only and is lost when the service stops.
- A copy of the JWKS is kept at `JWKS_FILE`, so a service that restarts while NICE is down still verifies tokens that have not expired.
- Without `NICE_SERVICE_API_KEY`, the service still runs and logs a warning at start: the access change feed is off (revocation takes effect only when the token expires, at most 30 minutes), `DELETE /devices/{id}` answers `503`, and so does every call with a token that carries `perms_ref`.
- A token whose permissions do not fit it carries `perms_ref` in place of `perms`. NICE issues one to a caller whose `nadi` permissions exceed the token size limit (6 KB). `verify.NewHTTPResolver` fetches the permission list from NICE (`POST /api/v1/permission-resolutions`) once for each distinct list, checks it against `perms_ref`, and keeps it in memory. After that the service decides alone, also for other callers that hold the same permissions. When the permissions of the caller changed since the token was issued, NICE answers that the reference does not match and the service answers `401 token_stale`, so the client refreshes. When NICE cannot be reached and the list is not kept yet, the service answers `503`.

## Data per organization and project

A device belongs to one organization and one project. The handler builds the scope key `domain.Scope{OrgID, ProjectID, Subject, Actor}` from the claims of the verified token (`nice_org_id`, `prj`, `sub`, `act.sub`), the use case passes it to the repository, and the repository has no other way to name an organization or a project. A device of another scope is answered `404`. `project_id` in the query is ignored, and an unknown field in the body, `project_id` included, is refused `400 invalid_argument` `body`.

When `DATABASE_URL` is set, the service runs `migrations/` at start (a `schema_migrations` table, and an advisory lock so two processes never run them at once), then keeps the devices in PostgreSQL:

| Table | Columns |
|---|---|
| `tenants` | `org_id` (key, from `nice_org_id`), `created_at` |
| `devices` | `id` (uuid, shown as `dev_<32 hex>`), `org_id`, `project_id` (from `prj`), `created_by` (from `sub`), `acted_by` (from `act`, `NULL` without it), `name`, `serial_number`, `status`, `location`, `create_time`, `update_time`; index `(org_id, project_id)` |

Every query uses `WHERE org_id = $1 AND project_id = $2`, reads, updates and deletes by id included. A tenant is created with `INSERT ... ON CONFLICT DO NOTHING`, so two first requests at once make one row. There is no foreign key to NICE: organization, project and user IDs are kept as text, and organization or project names are not kept. Never edit a released migration; add a new pair of files.

## Agent attribution (`acted_by`)

A backend that exchanges the user's token through token exchange, for example [`../../agent-backend`](../../agent-backend/README.en.md), calls this service with a token whose `sub` is still the user and whose `act.sub` claim is the `client_id` of that backend's service client. The service verifies that token with the same steps. The actor gains no rights: the permissions are still the `perms` of the token, the user's permissions cut down to what the backend's service declared for this dependency.

A device created with such a token records both:

```json
{"id": "dev_...", "name": "Sensor Suhu", "serial_number": "SN-1", "status": "active", "location": "Gudang A", "created_by": "usr_...", "acted_by": "<client_id of agen-backend>"}
```

Without `act`, there is no `acted_by` field. The code reads it from `Claims.Actor` of `niceauth/verify` (`internal/adapter/rest/device/create_device_handler.go`), and the test `TestDeviceCreatedByAnAgentRecordsTheActor` uses a test token that carries `act`.

## Prerequisites

- The SDK comes from the public module `github.com/ABA-Developer/nice-auth-sdk` (`v0.2.2` in `go.mod`), so this example builds without the `nice` repo. The `nice` repo next to `example/` is needed only to run a local NICE and for `nice/scripts/dev-token.sh`.
- Go 1.27, `curl`, `jq`, and `openssl` (for `nice/scripts/dev-token.sh`).
- A dev NICE running, at `http://localhost:8080` by default (`cd ../../../nice && make db && make migrate && make dev`). NICE at another address works too: put it in `NICE_ISSUER` in `.env` and in `NICE` in the checklist shell.

## Configuration

Copy `.env.example` to `.env`. The service reads `.env` from the directory it runs in; a variable set in the environment wins over the file.

| Variable | Default | Meaning |
|---|---|---|
| `NICE_ISSUER` | required | the NICE issuer, exactly as the `iss` claim of its tokens. Without it the service stops with a message naming `NICE_ISSUER` |
| `LISTEN_ADDR` | `127.0.0.1:8081` | listen address |
| `JWKS_FILE` | `data/jwks.json` | JWKS copy on disk (`data/` is not committed) |
| `NICE_CLIENT_ID`, `NICE_CLIENT_SECRET` | required | the confidential OAuth client of the UI (step 2). Without both the service stops with a message naming the variable; the secret is never printed |
| `PUBLIC_URL` | `http://localhost:8081` | the UI origin the browser sees; redirect URI = `PUBLIC_URL/auth/callback`. Development with Vite, and Docker: `http://localhost:5181` |
| `POST_LOGOUT_URL` | `PUBLIC_URL/` | where the browser goes after **Keluar** ended the NICE session; it must be a post-logout redirect URI of the client (step 2). `none`: the signed-out page of NICE |
| `SESSION_IDLE_TIMEOUT` | `8h` | how long a browser session lives without use |
| `WEB_DIR` | `../web/dist` | the built UI served at `/`; empty in Docker, where the UI has a container of its own |
| `DATABASE_URL` | empty | a `postgres://` URL for the devices; empty keeps them in memory. Its value is never printed |
| `CORS_ALLOWED_ORIGINS` | `http://localhost:5180` | other browser origins allowed to call with a Bearer token, comma separated, for `public-client-pkce`. The UI of this example needs no CORS since it shares the origin |
| `NICE_SERVICE_API_KEY` | empty | API key of a platform Service Account with the `nice.service` role (step 9); turns on the feed, the online check, and the resolution of `perms_ref` |
| `SMOKE_SA_ID`, `SMOKE_API_KEY` | empty | read only by `scripts/smoke.sh`: a tenant Service Account and its API key (step 10) |

## NICE setup checklist

Run from the `example/sharedservice-oauth/backend` directory. Console steps name the page; the `curl` snippets are the equivalent.

First, prepare shell variables. Tokens come from `nice/scripts/dev-token.sh` (client `nice-console` with the NICE dev default redirect `http://localhost:5173/callback`; if the account uses two-step verification, set `TOTP_SECRET`, see the script header). Tokens last 30 minutes; repeat when they expire.

```bash
export NICE=${NICE:-http://localhost:8080}   # address of NICE, same as NICE_ISSUER in .env; dev-token.sh reads it too

# your dev Platform Admin account
read -rp 'Platform Admin email: ' ADMIN_EMAIL; read -rsp 'Password: ' ADMIN_PASSWORD; echo
ADMIN_TOKEN=$(../../../nice/scripts/dev-token.sh "$ADMIN_EMAIL" "$ADMIN_PASSWORD"); unset ADMIN_PASSWORD

# your dev tenant organization owner account
read -rp 'Tenant owner email: ' OWNER_EMAIL; read -rsp 'Password: ' OWNER_PASSWORD; echo
OWNER_TOKEN=$(../../../nice/scripts/dev-token.sh "$OWNER_EMAIL" "$OWNER_PASSWORD"); unset OWNER_PASSWORD

ORG_ID=$(curl -sS "$NICE/api/v1/me/organization" -H "Authorization: Bearer $OWNER_TOKEN" | jq -r .organization.id)
curl -sS "$NICE/api/v1/organizations/$ORG_ID/projects" -H "Authorization: Bearer $OWNER_TOKEN" | jq '.projects[] | {id, name}'
PROJECT_ID=prj_...   # the tenant project that will use nadi
USER_ID=$(curl -sS "$NICE/api/v1/me/profile" -H "Authorization: Bearer $OWNER_TOKEN" | jq -r .profile.user_id)
```

### 1. NICE environment

Add to `nice/.env`, then restart NICE. Without these NICE refuses `http` endpoints and loopback addresses.

```text
NICE_OUTBOUND_ALLOW_HTTP=true
NICE_OUTBOUND_ALLOW_CIDRS=127.0.0.0/8
```

`NICE_OUTBOUND_ALLOW_CIDRS` is a comma-separated list of CIDRs. This service and its UI do not need `NICE_CORS_ALLOWED_ORIGINS`: the browser only navigates to the NICE sign-in page.

### 2. OAuth client of the UI and run the service

The service does not start without the OAuth client of the UI, so the client comes first: a **confidential** client in a project of the platform organization (a client of a tenant organization cannot be bound to a service). The binding to `nadi` follows once the service is registered (step 2 of [`../README.en.md`](../README.en.md#nice-setup-checklist)). Console: Platform Admin, platform organization, **Project**, then the **OAuth client** page of that project: confidential type, grants `authorization_code` and `refresh_token`, two redirect URIs, and two post-logout redirect URIs (`http://localhost:5181/` and `http://localhost:8081/`, where **Keluar** returns).

```bash
PLATFORM_ORG_ID=$(curl -sS "$NICE/api/v1/me/organization" -H "Authorization: Bearer $ADMIN_TOKEN" | jq -r .organization.id)
UI_PROJECT_ID=$(curl -sS "$NICE/api/v1/organizations/$PLATFORM_ORG_ID/projects" -X POST \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"NADI UI","slug":"nadi-ui"}' | jq -r .project.id)
CLIENT=$(curl -sS "$NICE/api/v1/projects/$UI_PROJECT_ID/clients" -X POST \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"nadi","client_type":"CLIENT_TYPE_CONFIDENTIAL",
       "redirect_uris":["http://localhost:5181/auth/callback","http://localhost:8081/auth/callback"],
       "post_logout_redirect_uris":["http://localhost:5181/","http://localhost:8081/"],
       "grant_types":["authorization_code","refresh_token"]}')
OAUTH_CLIENT_ID=$(jq -r .oauth_client.id <<<"$CLIENT")
jq -r .oauth_client.client_id <<<"$CLIENT"   # into NICE_CLIENT_ID
jq -r .client_secret <<<"$CLIENT"            # into NICE_CLIENT_SECRET; shown only once
unset CLIENT
```

```bash
cp .env.example .env   # then fill NICE_CLIENT_ID and NICE_CLIENT_SECRET
make run
curl -sS http://127.0.0.1:8081/healthz
```

Leave it running in another terminal. For development with Vite, also set `PUBLIC_URL=http://localhost:5181`. The other keys in `.env` are filled in at steps 9 and 10.

### 3. Register `nadi`

Console: Platform Admin, **Shared Service**, **Daftarkan Shared Service**. Write the endpoint as `http://127.0.0.1:8081`, not `localhost`, so NICE never tries `::1`. `auth_mode` need not be sent; its default is `nice_token`.

```bash
curl -sS "$NICE/api/v1/shared-services" -X POST \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"slug":"nadi","name":"NADI","endpoint":"http://127.0.0.1:8081","health_path":"/healthz"}'
```

### 4. Import `/openapi.json`

Console: the `nadi` detail page under **Shared Service**, catalog import (preview, then apply).

```bash
DOCUMENT=$(curl -sS http://127.0.0.1:8081/openapi.json | jq -Rs .)
PREVIEW=$(curl -sS "$NICE/api/v1/shared-services/nadi/catalog-imports" -X POST \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d "{\"document\":$DOCUMENT}")
printf '%s' "$PREVIEW" | jq '{added: [.diff.added[] | {key, permission, sensitive}], roles: [.diff.roles[] | .key]}'
IMPORT_ID=$(printf '%s' "$PREVIEW" | jq -r .import_id)
HASH=$(printf '%s' "$PREVIEW" | jq -r .hash)
curl -sS "$NICE/api/v1/shared-services/nadi/catalog-imports/$IMPORT_ID/apply" -X POST \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d "{\"hash\":\"$HASH\"}"
```

The preview must show five operations, four permissions (`deleteDevice` sensitive), and the derived roles `nadi.viewer` and `nadi.admin` and the additional role `nadi.editor` (NICE derives `nadi.operator` itself, so it is not declared).

### 8. Bind a user to an nadi role

Console: tenant project, **IAM**. IAM copies the catalog and the activation asynchronously: if the answer is `unknown_role` or `service_not_active`, wait a few seconds and retry. `echo "$BINDING_ID"` must print `rb_...`, not `null`.

```bash
BINDING_ID=$(curl -sS "$NICE/api/v1/projects/$PROJECT_ID/role-bindings" -X POST \
  -H "Authorization: Bearer $OWNER_TOKEN" -H 'Content-Type: application/json' \
  -d "{\"principal_type\":\"PRINCIPAL_TYPE_USER\",\"principal_id\":\"$USER_ID\",\"role\":\"nadi.editor\"}" | jq -r .role_binding.id)
```

`nadi.editor` does not hold `nadi.devices.delete`; use `nadi.admin` to try deleting devices.

### 9. Platform Service Account with `nice.service` (feed, online check, and `perms_ref`)

The Platform Admin creates a Service Account in a project of the platform organization (create the project if there is none), gives it the `nice.service` role, then an API key (there is no `allowed_services`: the rights come from the role of the Service Account). Console: **Service Account** in the platform organization project, then **Pengguna platform** for the `nice.service` role.

```bash
PLATFORM_ORG_ID=$(curl -sS "$NICE/api/v1/me/organization" -H "Authorization: Bearer $ADMIN_TOKEN" | jq -r .organization.id)
PLATFORM_PROJECT_ID=$(curl -sS "$NICE/api/v1/organizations/$PLATFORM_ORG_ID/projects" -X POST \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"slug":"service-readers","name":"Service readers"}' | jq -r .project.id)
FEED_SA_ID=$(curl -sS "$NICE/api/v1/projects/$PLATFORM_PROJECT_ID/service-accounts" -X POST \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"nadi-feed","description":"Access change feed and online check for nadi"}' | jq -r .service_account.id)
curl -sS "$NICE/api/v1/admin/role-bindings" -X POST \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d "{\"principal_type\":\"PRINCIPAL_TYPE_SERVICE_ACCOUNT\",\"principal_id\":\"$FEED_SA_ID\",\"role\":\"nice.service\"}"
curl -sS "$NICE/api/v1/projects/$PLATFORM_PROJECT_ID/api-keys" -X POST \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d "{\"service_account_id\":\"$FEED_SA_ID\",\"name\":\"nadi-feed\"}" | jq -r .key
```

The key is shown once. Put it in `NICE_SERVICE_API_KEY` in `.env`, then restart `make run`; the feed warning at start is gone.

IAM learns about a new Service Account asynchronously, so a binding made right after creating it can be answered 400 `principal_not_in_org`. Wait a few seconds and repeat the binding; the same holds for step 10.

For a deployment with several replicas, note that each replica keeps its revocation marks in its own memory, so each replica opens its own long poll on the feed. NICE lets one Service Account hold only 4 long polls at once. If a fifth or later replica uses a key of the same Service Account, it keeps getting `429 too_many_waits`. That replica then goes degraded: the log shows "the access change feed is silent", and revocation takes effect only when the token expires. So create one `nice.service` Service Account for each group of at most 4 replicas.

### 10. Tenant Service Account for the smoke test

Console: tenant project, **Service Account** (account and API key) and **IAM** (binding).

```bash
SMOKE_SA_ID=$(curl -sS "$NICE/api/v1/projects/$PROJECT_ID/service-accounts" -X POST \
  -H "Authorization: Bearer $OWNER_TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"nadi-smoke"}' | jq -r .service_account.id)
curl -sS "$NICE/api/v1/projects/$PROJECT_ID/role-bindings" -X POST \
  -H "Authorization: Bearer $OWNER_TOKEN" -H 'Content-Type: application/json' \
  -d "{\"principal_type\":\"PRINCIPAL_TYPE_SERVICE_ACCOUNT\",\"principal_id\":\"$SMOKE_SA_ID\",\"role\":\"nadi.viewer\"}"
curl -sS "$NICE/api/v1/projects/$PROJECT_ID/api-keys" -X POST \
  -H "Authorization: Bearer $OWNER_TOKEN" -H 'Content-Type: application/json' \
  -d "{\"service_account_id\":\"$SMOKE_SA_ID\",\"name\":\"nadi-smoke\"}" | jq -r .key
echo "$SMOKE_SA_ID"
```

Put the Service Account id in `SMOKE_SA_ID` and the key in `SMOKE_API_KEY` in `.env`.

### 11. Smoke

```bash
scripts/smoke.sh
```

The script reads only `.env`, never prints a key or a token, and checks: NICE answers, `/healthz` answers, `GET /auth/session` without a cookie is answered `401 unauthenticated`, `GET /auth/login` redirects to `$NICE/oauth/authorize` with the `client_id` of `NICE_CLIENT_ID`, `GET /devices` without a token is answered `401 missing_token`, a Service Account token is issued through `client_credentials` with the scope `nice:aud:nadi` (`client_id` is the Service Account id, `client_secret` the API key), and `GET /devices` with that token is answered `200`. It exits with code 0 when everything passes. Failures point to checklist steps:

| Answer | Step likely missed |
|---|---|
| no `.env`, NICE or service unreachable | 2 (and NICE must be running) |
| `NICE_CLIENT_ID` or `NICE_CLIENT_SECRET` empty, `/auth/login` does not lead to NICE | 2 |
| `invalid_client` | 10: the Service Account id does not own the key, the key is revoked or expired, the account is disabled |
| `invalid_scope` | 3 to 7, or 10 (the project of the Service Account must activate `nadi`) |
| `403 permission_denied` from the service | 10: binding of the Service Account to an nadi role |

## Revocation test (optional)

Needs `NICE_SERVICE_API_KEY` set (step 9). A user token issued before the binding is revoked is refused with `401 token_stale`.

```bash
read -rsp 'Owner password: ' OWNER_PASSWORD; echo
USER_TOKEN=$(../../../nice/scripts/dev-token.sh "$OWNER_EMAIL" "$OWNER_PASSWORD" "" "openid nice:aud:nadi nice:prj:$PROJECT_ID"); unset OWNER_PASSWORD
curl -sS http://127.0.0.1:8081/devices -H "Authorization: Bearer $USER_TOKEN"     # 200
sleep 2
curl -sS -X DELETE "$NICE/api/v1/projects/$PROJECT_ID/role-bindings/$BINDING_ID" -H "Authorization: Bearer $OWNER_TOKEN"
sleep 2
curl -sS http://127.0.0.1:8081/devices -H "Authorization: Bearer $USER_TOKEN"     # 401 token_stale
```

The pause before revoking is needed because the feed works at one-second resolution: a token issued in the same second as the revocation is not caught.

## Trying permissions that do not fit a token (optional)

Needs `NICE_SERVICE_API_KEY` set (step 9). NICE limits a token to 6 KB, enough for about 65 to 100 permissions. A caller with more `nadi` permissions gets a token with `perms_ref` in place of `perms`, and `nadi` fetches the permission list from NICE once. `nadi` itself has only four permissions, so `scripts/large-catalog.sh` prints its document with extra operations that each declare one permission (`nadi.catalog_test.pNNN.read`). `nadi` does not serve those operations: they only make the permission list longer.

```bash
scripts/large-catalog.sh 150 > /tmp/nadi-large.json   # 154 permissions
```

1. Import `/tmp/nadi-large.json` as the catalog of `nadi` (step 4, with this file as the document) and apply it.
2. Make sure the user holds the `nadi.admin` role in the project (step 8). That role holds every active permission of `nadi`, so 154 now.
3. Sign in through the UI at `PUBLIC_URL`. The device list shows and a device can be created as usual.

What you can check:

```bash
read -rsp 'User password: ' USER_PASSWORD; echo
USER_TOKEN=$(../../../nice/scripts/dev-token.sh "$USER_EMAIL" "$USER_PASSWORD" "" "openid nice:aud:nadi nice:prj:$PROJECT_ID"); unset USER_PASSWORD
printf '%s' "$USER_TOKEN" | cut -d. -f2 | tr '_-' '/+' | base64 -d 2>/dev/null | jq '{perms_ref, perms}'   # perms_ref is set, perms is null
printf '%s' "$USER_TOKEN" | wc -c                                                                        # under 6144
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8081/devices -H "Authorization: Bearer $USER_TOKEN"   # 200
```

When NICE runs with `NICE_METRICS_ENABLED=true`, `nice_oauth_service_tokens_total{permissions="reference"}` goes up for every such token, and `nice_permission_resolutions_total{result="match"}` goes up only once however often `GET /devices` is called: `nadi` keeps the permission list after the first fetch. Without `NICE_SERVICE_API_KEY`, the same call answers `503 permissions_unavailable`.

To restore the catalog, import `docs/swagger.json` (or `/openapi.json`) again and apply it: the extra operations become `removed` and `nadi.admin` holds four permissions again.
