# `api_key` service example: `pengiriman` (Hono)

[Bahasa Indonesia](README.md)

A legacy service that knows only its own API key, registered in NICE as a SharedService in `api_key` mode with the slug `pengiriman`. Clients do not call it directly. They call the NICE proxy at `<NICE>/pengiriman/...` with a NICE JWT; NICE verifies the token, matches the operation against the catalog, checks the permission, then forwards the request to the service with the service credential in the `X-Api-Key` header and the caller's identity in the `X-Nice-*` headers.

```text
client --Authorization: Bearer <JWT>--> NICE /pengiriman/shipments
NICE   --X-Api-Key + X-Nice-Organization/Project/Principal--> http://127.0.0.1:8082/shipments
```

This service does not verify JWTs and does not check permissions. Both are the proxy's job. The service only checks `X-Api-Key`.

NICE contract followed: `nice/docs/api.md` sections "Service api_key dan proxy", "Kunci per Service Account (mirrored key)", and "Service Account: `client_credentials`", plus `nice/docs/gateway-integration.md` section "Service lama yang tidak bisa diubah".

Tested against nice revision: `c7a5086` (2026-11-13)

## Warning: `X-Nice-*` headers

The service trusts `X-Nice-Organization` (tenant) and `X-Nice-Principal` (actor) **only because** the request carries a valid credential. That credential proves the request came from the NICE proxy, and the proxy drops any `X-Nice-*` headers the client sent and sets them from the verified token. As a result, anyone who holds `SERVICE_CREDENTIAL` can claim to be any organization and any principal.

- Do not give `SERVICE_CREDENTIAL` to anyone but NICE.
- Do not expose this service to a public network. Keep `LISTEN_ADDR` on loopback (`127.0.0.1`), or restrict it with a firewall so that only NICE can reach it.

## Operations

| Operation | Credential | In `/openapi.json` | Catalog permission |
|---|---|---|---|
| `GET /shipments` | service or mirrored key | yes | `pengiriman.shipments.read` |
| `POST /shipments` body `{"destination"}` | service or mirrored key | yes | `pengiriman.shipments.create` |
| `POST /shipments/{id}/cancel` | service or mirrored key | yes | `pengiriman.shipments.cancel` |
| `POST /keys` body `{"label"}` | service credential only | no | - |
| `POST /keys/{key_id}/rotate` | service credential only | no | - |
| `DELETE /keys/{key_id}` | service credential only | no | - |
| `GET /healthz` | none | no | - |
| `GET /openapi.json` | none | no | - |

Shipment operations use `X-Nice-Organization` as the tenant and record `X-Nice-Principal` as `created_by`. Data is kept in memory per organization and is lost on restart. Every error has the shape `{"error":"<code>"}`, plus `error_description` for `invalid_argument`:

| Status | `error` | When |
|---|---|---|
| 401 | `unauthorized` | `X-Api-Key` is missing or does not match |
| 400 | `missing_organization` | a credentialed request to a shipment operation without `X-Nice-Organization` |
| 400 | `invalid_argument` | `destination` empty or longer than 200 characters (`error_description: "destination"`), body is not JSON (`"body"`), or invalid `label` (`"label"`) |
| 415 | `unsupported_media_type` | a `POST /shipments` body without `Content-Type: application/json` |
| 404 | `not_found` | the shipment is not in that organization, unknown key, or unknown path |
| 409 | `already_cancelled` | the shipment is already cancelled |
| 403 | `admin_credential_required` | a mirrored key calls a key operation |

The `/openapi.json` document (OpenAPI 3.0) is generated by `@hono/zod-openapi` from the shipment routes only. The key operations, `/healthz`, and `/openapi.json` are registered as plain Hono routes, so they never become catalog operations that can be called through the proxy (the proxy answers `POST <NICE>/pengiriman/keys` with 404).

### Key operations for mirrored keys

NICE calls the three key operations after step 12 (optional). NICE sends the service credential in `X-Api-Key` and no `X-Nice-*` headers.

| Operation | Answer |
|---|---|
| `POST /keys` body `{"label":"<uuid>"}` | 201 `{"key_id","key"}`. The key is accepted by the shipment operations at once |
| `POST /keys/{key_id}/rotate` | 200 `{"key_id","key"}` with the same `key_id`; the old key is rejected at once. 404 when the id is unknown or already revoked. The `{"key_id"}` body NICE sends is ignored |
| `DELETE /keys/{key_id}` | 204 (also for a key that is already revoked); 404 when the id is unknown. NICE treats 404 as already revoked |

A key is `pgk_` + 32 random bytes in base64url, and its id is `key_` + 24 hex characters. `KEYS_FILE` (default `data/keys.json`) stores only `{key_id, label, sha256, status, create_time}`, never the key itself. The file is written to a temporary file in the same directory, `fsync`ed, then `rename`d, so it is never half written and keys stay valid after a restart. The service refuses to start on a damaged file instead of overwriting it.

The `X-Api-Key` middleware (`src/auth.ts`) hashes the presented value with SHA-256 and compares it with `crypto.timingSafeEqual` against the hash of the service credential and the hash of every active mirrored key. The credential kind (`service` or `mirrored`) is recorded on the request context and in the log. Credential and key values are never logged.

## Requirements

- Node.js 22.18 or later (runs `.ts` directly through type stripping, no build) and npm.
- `curl` and `jq` for the checklist and the smoke script.
- A running NICE dev (`make dev` in `nice/`, `http://localhost:8080` by default), with the `nice/` repo next to `example/`. For NICE at another address, set `NICE_URL` in `.env`; the checklist and the smoke test read it from there.

## Configuration

Copy `.env.example` to `.env`. The service reads environment variables; `npm run dev` and `npm start` load `.env` through `node --env-file-if-exists=.env`, and variables already set in the environment are not overridden.

| Variable | Default | Meaning |
|---|---|---|
| `SERVICE_CREDENTIAL` | (required) | The credential NICE sends in `X-Api-Key`. Generate it with `openssl rand -hex 32`. Without it the service stops at start with a message naming the variable |
| `LISTEN_ADDR` | `127.0.0.1:8082` | Listen address `host:port` |
| `KEYS_FILE` | `data/keys.json` | Mirrored key file (hashes only) |
| `NICE_URL` | `http://localhost:8080` | NICE address, used only by `scripts/smoke.sh` |
| `SMOKE_SA_ID` | | Tenant Service Account id (`sa_...`) for the smoke test, from step 9 |
| `SMOKE_SA_API_KEY` | | That Service Account's API key (`nice_sk_...`), from step 11 |

`.env` and `data/` are not committed.

## Running

```bash
cd example/shared-service-apikey
npm install
cp .env.example .env            # then set SERVICE_CREDENTIAL to the output of: openssl rand -hex 32
npm run dev                     # node --watch; or npm start without watch
curl -s http://127.0.0.1:8082/healthz        # {"status":"ok"}
curl -s http://127.0.0.1:8082/openapi.json | jq '.paths | keys'
```

## Tests

```bash
npm test             # Vitest, calls app.request() with no network and no NICE
npm run typecheck    # tsc --noEmit
```

The tests write the key file to a temporary directory per test and rebuild the app from the same file to simulate a restart.

## NICE setup checklist (manual)

Every step on the NICE side is manual, through NICE Console or `curl`. Run the `curl` snippets below from this example's directory, in one shell session:

```bash
cd example/shared-service-apikey
set -a; . ./.env; set +a          # SERVICE_CREDENTIAL and NICE_URL from .env
NICE=$NICE_URL
```

### 1. NICE environment

Add to `nice/.env`, then restart NICE (`make dev`):

```bash
NICE_OUTBOUND_ALLOW_HTTP=true
NICE_OUTBOUND_ALLOW_CIDRS=127.0.0.0/8
```

Without both, NICE refuses `http://` endpoints and loopback addresses for registration, import, health probes, the proxy, and key operations. `NICE_OUTBOUND_ALLOW_CIDRS` is a comma-separated list of CIDRs.

### 2. Run the service

Follow [Running](#running). The service must be running before step 4, because NICE checks the endpoint and fetches `/openapi.json` from it.

### 3. Admin tokens

Get two access tokens with `nice/scripts/dev-token.sh`: one for your dev Platform Admin account (catalog and entitlement steps), and one for an owner or admin of the tenant organization that will use the service (project steps). Passwords are read without echo and stay out of the shell history. If the account uses two-step verification, set `TOTP_SECRET` (see the comments in that script).

```bash
read -rp 'Platform Admin email: ' ADMIN_EMAIL; read -rsp 'Password: ' ADMIN_PASSWORD; echo
ADMIN_TOKEN=$(NICE=$NICE ../../nice/scripts/dev-token.sh "$ADMIN_EMAIL" "$ADMIN_PASSWORD")
read -rp 'Tenant organization owner email: ' OWNER_EMAIL; read -rsp 'Password: ' OWNER_PASSWORD; echo
OWNER_TOKEN=$(NICE=$NICE ../../nice/scripts/dev-token.sh "$OWNER_EMAIL" "$OWNER_PASSWORD")
unset ADMIN_PASSWORD OWNER_PASSWORD

ORG_ID=$(curl -sS "$NICE/api/v1/me/organization" -H "Authorization: Bearer $OWNER_TOKEN" | jq -r .organization.id)
curl -sS "$NICE/api/v1/organizations/$ORG_ID/projects" -H "Authorization: Bearer $OWNER_TOKEN" | jq '.projects[] | {id, slug, name}'
PROJECT_ID=prj_...                # pick a tenant project from the list above
```

Tokens last 30 minutes. If a later `curl` answers 401, get a new token.

### 4. Register the `pengiriman` service

Console: **Platform Admin > Shared Service**, register a new service in `api_key` mode. Or with `curl` (`jq` reads the credential value from the environment, so it never appears in a command's arguments):

```bash
jq -n '{slug: "pengiriman", name: "Pengiriman", endpoint: "http://127.0.0.1:8082", health_path: "/healthz",
        auth_mode: "api_key", upstream: {credential: {header: "X-Api-Key", value: env.SERVICE_CREDENTIAL}}}' |
  curl -sS -X POST "$NICE/api/v1/shared-services" -H "Authorization: Bearer $ADMIN_TOKEN" \
    -H 'Content-Type: application/json' -d @- | jq '.shared_service | {slug, auth_mode, status, credential}'
```

- `endpoint` is `http://127.0.0.1:8082`, not `localhost`. `localhost` may resolve to `::1`, which the service does not listen on and which is outside `127.0.0.0/8`.
- `base_path` is left empty, so `<NICE>/pengiriman/shipments` is forwarded to `http://127.0.0.1:8082/shipments`.
- `upstream.credential`: `header` `X-Api-Key`, **no** `scheme`, and `value` exactly equal to `SERVICE_CREDENTIAL`. The value is write-only: the response shows only `credential.header` and `credential.configured`. Replace it with `PUT /api/v1/shared-services/pengiriman/upstream/credential`.
- `health_path` `/healthz` is open without a credential, because the NICE probe sends none.

### 5. Import `/openapi.json`

Console: the `pengiriman` service page, import the catalog from a URL, then apply. Or preview and apply with `curl`:

```bash
PREVIEW=$(curl -sS -X POST "$NICE/api/v1/shared-services/pengiriman/catalog-imports" \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"url":"http://127.0.0.1:8082/openapi.json"}')
jq '{import_id, added: [.diff.added[]? | {key, method, path, permission}], roles: [.diff.roles[]? | {key, permissions}]}' <<<"$PREVIEW"
curl -sS -X POST "$NICE/api/v1/shared-services/pengiriman/catalog-imports/$(jq -r .import_id <<<"$PREVIEW")/apply" \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d "$(jq '{hash}' <<<"$PREVIEW")"
```

The preview must show exactly three operations: `listShipments` (`pengiriman.shipments.read`), `createShipment` (`pengiriman.shipments.create`), and `cancelShipment` (`pengiriman.shipments.cancel`), plus the roles `pengiriman.viewer` and `pengiriman.admin`.

### 6. Activate the service

Console: the `pengiriman` service page, activate. Or:

```bash
curl -sS -X POST "$NICE/api/v1/shared-services/pengiriman/activate" -H "Authorization: Bearer $ADMIN_TOKEN" | jq '.shared_service | {slug, status}'
```

### 7. Organization entitlement

Console: **Platform Admin > Organisasi**, pick the tenant organization, grant the `pengiriman` entitlement. Or:

```bash
curl -sS -X POST "$NICE/api/v1/organizations/$ORG_ID/entitlements" -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H 'Content-Type: application/json' -d '{"service":"pengiriman"}'
```

### 8. Activate in the project

Console (as the tenant owner): **Project > Product & Activation**, activate `pengiriman`. Or:

```bash
curl -sS -X PUT "$NICE/api/v1/projects/$PROJECT_ID/services/pengiriman/activation" -H "Authorization: Bearer $OWNER_TOKEN"
```

### 9. Tenant Service Account

Console: **Project > Service Account**, create a Service Account. Or:

```bash
SA_ID=$(curl -sS -X POST "$NICE/api/v1/projects/$PROJECT_ID/service-accounts" -H "Authorization: Bearer $OWNER_TOKEN" \
  -H 'Content-Type: application/json' -d '{"name":"pengiriman-smoke","description":"Smoke test contoh pengiriman"}' |
  jq -r .service_account.id)
echo "$SA_ID"
```

Set `SMOKE_SA_ID` in `.env` to that value.

### 10. Role binding

Console: **Project > IAM**, give that Service Account the `pengiriman.admin` role (or `pengiriman.viewer`, which is enough for the smoke test since it only calls `GET /shipments`). Or:

```bash
curl -sS -X POST "$NICE/api/v1/projects/$PROJECT_ID/role-bindings" -H "Authorization: Bearer $OWNER_TOKEN" \
  -H 'Content-Type: application/json' \
  -d "{\"principal_type\":\"PRINCIPAL_TYPE_SERVICE_ACCOUNT\",\"principal_id\":\"$SA_ID\",\"role\":\"pengiriman.admin\"}"
```

IAM learns about a new Service Account asynchronously. A binding made right after step 9 can be answered 400 `principal_not_in_org`, and one made right after step 8 400 `service_not_active`; wait a few seconds and repeat.

### 11. Service Account API key

Console: the same Service Account page, create an API key whose allowed services include `pengiriman`. Or:

```bash
curl -sS -X POST "$NICE/api/v1/projects/$PROJECT_ID/api-keys" -H "Authorization: Bearer $OWNER_TOKEN" \
  -H 'Content-Type: application/json' \
  -d "{\"service_account_id\":\"$SA_ID\",\"name\":\"pengiriman-smoke\",\"allowed_services\":[\"pengiriman\"]}" |
  jq '{id: .api_key.id, key}'
```

`key` is shown only once. Save it as `SMOKE_SA_API_KEY` in `.env`. This key is exchanged for a token at `/oauth/token` and is never sent to the service.

### 12. Optional: upstream key operations (mirrored keys)

After this step NICE stops using `SERVICE_CREDENTIAL` for client traffic. NICE creates one key per Service Account that holds a `pengiriman` permission through `POST /keys`, stores it wrapped with the KEK, and the proxy sends the calling Service Account's own key in `X-Api-Key`. `SERVICE_CREDENTIAL` is still used, but only by NICE to call the three key operations.

**As a result, only Service Accounts can call `pengiriman` through the proxy.** NICE users get 403 `service_account_required`, and a Service Account whose key is not active yet gets 503 `upstream_key_unavailable`.

Console: the `pengiriman` service page, item **Operasi kunci upstream**, fill in the three operations as below. Or with `curl` (needs `nice.platform.catalog.manage`):

```bash
curl -sS -X PUT "$NICE/api/v1/shared-services/pengiriman/upstream/key-operations" \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' -d '{
  "key_operations": {
    "generate": {"method": "POST", "path": "/keys"},
    "rotate": {"method": "POST", "path": "/keys/{key_id}/rotate"},
    "revoke": {"method": "DELETE", "path": "/keys/{key_id}"}
  }
}'
```

Paths are relative to `endpoint` + `base_path`, and NICE replaces `{key_id}` with the key id. To check the result:

- NICE sweeps active Service Accounts at start and on every role, catalog, or entitlement change (at least 30 seconds apart), and syncs one Service Account when its binding changes. Saving the key operations does not start a sweep by itself: when the Service Account already had its binding (step 10), restart NICE or remove and recreate the binding. After that the service log shows `key generated key_id=key_... label=<uuid>`. The label is the Service Account id without the `sa_` prefix.
- `jq . data/keys.json` shows a key whose `label` equals `SA_ID` without `sa_`, with `status` `active`, and no key value.
- A superadmin can see key metadata at `GET /api/v1/service-account-keys?service=pengiriman` (Console: **Platform Admin > Kunci Service Account**).
- `scripts/smoke.sh` still passes, and the service log now records `credential=mirrored` for proxied requests.

Up to nice revision `c7a5086`, the proxy did not use mirrored keys because the proxy route table dropped the per-account flag, so the proxy kept sending `SERVICE_CREDENTIAL` and the log recorded `credential=service`. The bug was fixed in nice `2638605`: mirrored keys now really reach the upstream, the smoke test passes with `credential=mirrored`, and a NICE user gets 403 `service_account_required`.

Notes:

- Do not delete `data/keys.json` after this step. The keys NICE holds would no longer be accepted, and the proxy passes the service's 401 through.
- There is no API to remove only the key operations. NICE forgets them only when the service mode is switched to `nice_token` through `PUT /api/v1/shared-services/pengiriman` while the service is disabled, and that is refused with 409 `keys_not_revoked` while any key is not yet revoked. Run this step on a NICE dev you can reset.

## Smoke test

After steps 1 to 11, with the service running:

```bash
scripts/smoke.sh
```

The script reads only `.env`, never prints the credential, the API key, or the token, and checks that:

1. a direct `GET http://127.0.0.1:8082/shipments` without `X-Api-Key` answers 401;
2. NICE is reachable at `NICE_URL`;
3. `GET <NICE>/pengiriman/shipments` without a token answers 401 from the proxy;
4. a Service Account token is issued through `client_credentials` with `scope=nice:aud:pengiriman`;
5. `GET <NICE>/pengiriman/shipments` with that token answers 200.

```text
ok    langsung ke service tanpa key: 401
ok    proxy tanpa token: 401
ok    token Service Account (scope nice:aud:pengiriman)
ok    GET http://localhost:8080/pengiriman/shipments lewat proxy: 200
smoke lulus
```

On failure the script exits non-zero and names the checklist step that was most likely missed (its messages are in Indonesian):

| Symptom | Step |
|---|---|
| no `.env`, or the service does not answer | 2 |
| NICE unreachable | 1 |
| proxy 404 without a token | 4, 5 |
| proxy 503 `service_disabled` | 6 |
| token `invalid_client` | 9, 11 |
| token `invalid_scope` | 6, 7, 8, 11 |
| proxy 403 `permission_denied` | 10, 11 |
| proxy 401 `{"error":"unauthorized"}` from the service | 4 (credential mismatch), 12 |
| proxy 503 `upstream_key_unavailable` | 12 |
| proxy 502 or 504 | 1, 2, 4 |

Calling the other operations through the proxy with a Service Account token:

```bash
set -a; . ./.env; set +a         # loads the SMOKE_SA_ID and SMOKE_SA_API_KEY you just filled in
TOKEN=$(curl -sS "$NICE/oauth/token" -d grant_type=client_credentials -d scope=nice:aud:pengiriman \
  --data-urlencode "client_id=$SMOKE_SA_ID" --data-urlencode client_secret@- \
  < <(printf '%s' "$SMOKE_SA_API_KEY") | jq -r .access_token)
curl -sS -X POST "$NICE/pengiriman/shipments" -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d '{"destination":"Gudang Timur, Surabaya"}'
curl -sS -X POST "$NICE/pengiriman/shipments/<id>/cancel" -H "Authorization: Bearer $TOKEN"
```
